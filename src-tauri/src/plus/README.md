# plus/ module index

Toolport+ additions (D-010). Full overview: `docs/toolport-plus.md`.

- `mod.rs`: `plus.*` handler table and `dispatch` behind the single `plus_invoke` IPC command.
- `ctl/`: `toolportctl` command table, flag parsing and JSON/human output; commands with a typed operation only translate flags into its arguments and word the result.
- `auth/`: login-expiry probes, status cache, gateway state, status surfaces.
- `context/`: layered rules deploy, what-loads viewer, folder profiles; `manage` is the shared core under `toolportctl context init|status|client|profile|disable` and the `plus.context.*` handlers of the same names. `measure` asks headless Claude Code for the real token count of a folder, per variant, behind a per-version cache (`toolportctl context measure`, the `context_measure` tool, `loads --measured`).
- `compression/`: compression policy, launch plan, savings ledger; `manage` holds the command cores (`enable`, `disable`, `sync`, `seal`, `doctor`, `status`, ...) that `toolportctl compression`, the `plus.compression.*` handlers (`handlers`) and the selfmcp `compression_*` tools share. `verify`, `ledger summary` and `run --plan` still live in `ctl/compression.rs`, and their `plus.compression.{verify,ledger,plan}` handlers re-encode their JSON arguments as flags for it.
- `skills/`: skill parser, lockfile, lint, transpilers (each declares its `Capabilities`: project-only, append-mode); `kind` (`ContentKind`) is the discovery and parse walk that skills, agents and styles share; `api` holds the typed operations (`list_skills`, `get`, `lint`, `diff`, `status`, `sync`, `transpilers`: `Args` in, JSON out) that `toolportctl skills ls|lint|diff|status|sync`, the `plus.skills.{list,lint,diff,status,sync}` handlers (`handlers`) and the selfmcp `skills_*` read and sync tools only adapt; `skills` imports neither `ctl` nor `selfmcp`. `ops` is the shared core under the lifecycle commands (`clean`, `uninstall`, `resolve`) and supplies the diff and status rows `api` serves. `sync_report` builds the entry and collision rows that `skills sync` reports (`api::sync`; `plus.skills.resolve` shares the collision rows). `skills/agents/` holds the agent transpilers and `manage`/`handlers`, the core under `toolportctl agents` and the `plus.agents.*` handlers (sync, clean and uninstall share `ops` and `sync_scoped` with the selfmcp `agents_sync` tool). `skills/styles/` holds the style transpilers and `manage`/`handlers`, the core under `toolportctl styles` and the `plus.styles.*` handlers (sync, apply and remove share `manage` with the selfmcp style tools, clean shares `ops`). `tap_ops` is the shared core under `toolportctl skills tap|search|install`, the `plus.skills.tap*`, `search` and `install` handlers (`tap_handlers`) and the selfmcp `skills_tap_*`, `skills_search` and `skills_install` tools; the tap list is `taps.json` beside the registry (`taps`), the clones live under `taps/` there, and git goes through `git.rs` only.
- `direct/`: opt-in direct client entries (D-055): `mod.rs` is the shared core under `toolportctl client direct add|rm|ls`, the `plus.client.directAdd|directRm|directLs` handlers (`handlers`) and the selfmcp `client_direct_*` tools; `record` is the ownership record under `plus.directEntries`, `launcher` is `toolportctl direct run`. The per-format entry writer is `clients::set_direct_entry`.
- `profiles/`: shared core under `toolportctl profile ls|create|edit|rm`, `client edit|import`, the `plus.profile.*` and `plus.client.edit|import` handlers and the selfmcp profile tools (`mutate` plans on a read-only copy, so a rejected edit or a dry run writes nothing).
- `sources/`: where every skill, command, agent, rule and CLAUDE.md comes from (D-063). `mod.rs` holds the `SourceDetector` trait, the scan engine (budgets, cache flush, selectors, shadow pass) and `host_world`/`scan_host`; one file per detector (`repo`, `client`, `vendored`, `plugin`, `org`, `account`, `library`, `tap`, `loose`, `inert`) that only uses `fsx` and `gitx`; `roots` is the `sources root add|rm|ls` core (`PlanV1` in, `ResultV1` out). `toolportctl sources`, the selfmcp `sources_ls` tool and `skills::api::list_skills` with `--source` share it; it imports neither `ctl` nor `selfmcp`.
- `plan.rs`: `PlanV1` and `ResultV1`, the plan and result shapes of the GUI-wave writers.
- `sync/`: encrypted cross-machine sync.
- `import_mcpm/`: mcpm to registry mapping and tool-reference rewrite.
- `selfmcp/`: self-management MCP server: 97 tools and 11 resources. A tool validates its arguments, checks its tier, calls the typed operation (`skills::api`, `status`, `client_sync`, `servers::uninstall`, `compression::manage`, ...) and scrubs the result; production code does not import `ctl`. `state` (skills, agents and styles lifecycle) and `compression` are thin adapters over the `plus.*` handlers and `compression::manage` cores that the ctl commands run; a writing tool there defaults `dry_run` to true and a tier 3 or 4 one needs `confirm` only to apply.
- `update/`: server update checks and apply.
- `obs/`: transcript indexer, loopback OTLP receiver (`receiver`, hosted by the gateway through `otel_host`), `otel_setup` (the `obs otel` enable, disable and status core) and `combine` (OTel and transcript dedupe).
- `plugins/`: the one reader of Claude Code plugins and hooks (D-074, D-075): `claude plugin list|details|configure --json` when the binary is there (`claude`, `installed`, `cli`), the plugin files otherwise (`installed`, `manifest`), effective `enabledPlugins` and hook switches over the user, project, local and managed settings (`settings`), the `hooks ls` inventory (`hooks`) and the `plugins ls|show` rows (`report`); `api` is what `toolportctl plugins|hooks` and the selfmcp `plugins_ls`, `plugins_show` and `hooks_ls` tools call. Nothing in it starts a hook, a plugin or an MCP server; the only child process is `claude` with fixed `plugin` arguments. `cc/` and the `plugin` source detector read through it.
- `cc/`: Claude Code plugin list and update.
- `council/`: council downstream server definition.
- `servers.rs`: server lookup (`find`, `named`), `fields_from`, the add that checks the name under the registry lock (`add_returning_id`) and `uninstall`, shared by `toolportctl server new|edit|install|uninstall` and the selfmcp `servers_install`, `servers_update_config` and `servers_uninstall` tools.
- `op.rs`: `OpError` and `ErrorKind`, the error of the typed operations; `ctl` aliases it as `CtlError` (the kind picks the exit code) and `selfmcp` maps it to `ToolError`.
- `status.rs`: `snapshot`, the read-only view of the data directory and registry, with the `status` and `doctor` JSON that `toolportctl status|doctor`, the selfmcp `where_am_i` and `doctor` tools and `mcpm://status` serve.
- `client_sync.rs`: client config pruning and `sync`, shared by `toolportctl client sync`, `server uninstall` and the selfmcp `clients_sync` tool.
- `redact.rs`: `scrub`, which masks live secret values and values under sensitive keys in selfmcp results and in the `plus.skills.{list,lint,status,sync}` handlers.
- `jsonfs.rs`: `read_json`, tolerant typed JSON read (None on missing or invalid).
- `testutil.rs` (test only): `DataDirFx`, data-dir lock plus override plus temp dir with the required drop order.

## Adding a `toolportctl` command group

A group is a spec table plus handlers; no parsing code.

1. Declare the flags per command in the handler's module (`ctl/flags.rs`):
   `const SYNC: Spec = Spec { flags: &[switch("--dry-run"), value("--path").alias(&["--repo"]).needs("a directory")], ..Spec::PLAIN };`.
   `switch`, `value` and `greedy` build flags; `.alias`, `.needs`, `.count`, `.nonempty` refine them. The style fields (`inline`, `unknown`, `operands`, `dashes`) pick the wording and edge cases; `Spec::NONE` is a command without arguments.
2. Write the handler: `let flags = SYNC.parse(rest)?;`, then `flags.on("--dry-run")`, `flags.one("--path")`, `flags.all(..)`, `flags.operands()`. Return `CtlError::usage`, `not_found`, `conflict` or `failed("code", msg)`.
3. Add one `cmd(&["group", "sub"], "summary", module::handler)` row per command to `COMMANDS` in `ctl/mod.rs`, plus a row for the bare group whose handler returns the group usage error. `.no_options()` is only for commands that must reject unknown `-x` tokens at the top level.
4. Pin the usage and error strings first: add argv lists to `CASES` in `ctl/usage_pins_tests.rs` and bless them with `UPDATE_GOLDEN=1 cargo test --no-default-features --lib usage_and_error_text`. Also classify the command in `tests/ctl_smoke.rs` and `tests/hardening_leak.rs`.
5. Give every command a safety row in `ctl/policy.rs` (`ROWS`: tier, `.dry()`/`.plan()`/`.unless(..)` preview, `.needs(..)`, `.spec(&[&module::SPEC])`, `.args(..)`), a sub-command a `sub(..)` row in `SUBS`, and every new flag a type and effect text in `ctl/commands_json.rs` (`GLOBAL`, or `OVERRIDES` for one command). `cargo test --lib plus::ctl::policy_tests` names what is missing; `toolportctl commands --json` is what the GUI reads.
6. Add the command (and a tool that runs it) to `src/plus/gui-parity.json`, re-bless the goldens in `tests/fixtures/ctl-envelopes/` with `CTL_ENVELOPE_BLESS=1 cargo test --no-default-features --test ctl_contract`, and say in the commit why the registry changed. `cargo test --test gui_parity` and `vitest src/plus/guiParity.test.ts` print the line to paste.
